# Route 机制设计（v0.1 自举候选）

> 本文件是 `route-intake` 技能的配套设计文档。定性：v0.1 自举候选，全部规则为**待校准假设**，
> 由真实项目轨迹反馈修正（SEED/scaling.summary.md 明示：结论是特定任务分布上的经验规律，非定律）。

## 一、新任务如何判断单 / 多 agent

### 1.1 任务属性表（route-intake 第 4 步）

| 属性 | 取值 | 定义 |
|---|---|---|
| 并行度 | 高/低 | 能否拆成互不依赖的独立单元 |
| 串行依赖 | 高/低 | 下一步是否强等上一步结论 |
| 工具密度 | 高/低 | 单位任务的外部调用数量 |
| 错误代价 | 高/低 | 出错后果的严重性与不可逆性 |
| 可独立验证 | 是/否 | 子结果能否单独判对错 |
| 是否软件工程 | 是/否 | 否 → 必须走领域抽象映射，不套软件术语 |

### 1.2 判定规则（保守默认：单 agent）

1. **默认单 agent**：证据不足时不加人（scaling 结论：单 agent 基线已较强后，再加协调边际递减甚至负收益）。
2. **强制单 agent**：串行依赖 = 高；或错误代价 = 高且尚无集中校验设计。
3. **可考虑集中编排**（1 orchestrator + N 专家）：并行度 = 高 **且** 可独立验证 = 是 **且** 错误代价 = 低/中。需汇总时由 orchestrator 集中校验，禁止无校验的独立专家并跑（错误放大最严重，scaling 结论）。
4. **工具密度 = 高**：优先单 agent + 工具，不盲目加人（协调开销吃掉推理预算）。
5. **多 agent 决策必须落地前显式设计集中校验与回放**；未设计完成前不得启动。

### 1.3 校准机制

- 每次任务轨迹记录：实际 agent 数、是否命中强制单 agent 条件、结果质量（六维打分）；
- 积累 ≥5 条轨迹后审视阈值是否需调整；调整本身走 GATE 级 B（架构规则修改），附 before/after 对比。

## 二、什么条件下判定"当前底座不适配"

不适配 = 底座无法承载此任务，任务结束时**必须**发起对 BASE 的修改提案。

### 2.1 判定条件（满足任一即不适配）

1. **领域盲区**：领域完全不在种子覆盖范围内，且无等价抽象可映射；
2. **维度失语**：任务属性表有 ≥2 项无法用现有维度表达（现有维度本身不够用）；
3. **铁律冲突**：执行中反复需要绕过铁律才能推进（这是底座规则缺陷信号，不是"再忍忍"）；
4. **系统性失分（本轮新增候选）**：六维回归探针中某维连续 ≥2 轮 <1 分——表明底座存在结构性缺陷而非单任务失误。

### 2.2 适配判断的落地要求

- 结论必须写入路由记录（`WORKSPACE/raw/route-<task>.md`），含理由——这是第六维 E2 的查验对象；
- 不适配时必须给出修改对象类型建议：pattern（单点经验）| skill（技能缺陷）| architecture（结构/规则缺陷）| constitution（元原则缺陷）。

## 三、"机制自改"提案的触发、审核、过渡期流程（对应 GATE 分级门槛 C）

> 本节描述宪法/元流程级修改（GATE 级 C，最严）的完整流程。级 A/级 B 复用同一管线，仅门槛项数不同。

### 3.1 触发

1. 任务出现 2.1 任一不适配条件，且路由记录中建议类型 = architecture 或 constitution；
2. 或 meta-* pattern（如 `meta-loop-bias`）被周期性体检命中；
3. 宪法/元流程级还须满足：≥2 个跨项目证据 或 探针集系统性失分（不凭单次感受发起）。

### 3.2 提案

- `PROPOSAL.md` 类型 = `constitution-amendment`（元流程结构调整用 `architecture`）；
- 内容按 GATE 级 C 要求：交叉验证方案 + 人工复审安排 + 旧版本 tag 保留说明 + CHANGELOG 更新项 + 过渡期双轨运行方案；
- 由 `propose-gate` 完成自检（自评仅供参考）。

### 3.3 审核（提案人与审核人分离）

1. `gate-review`（独立审核者）或人工跑回归探针，before/after 产物落盘 `WORKSPACE/regression-runs/`；
2. 双倍验证：交叉验证（非原领域探针）+ 人工复审（用户本人）；
3. 人工是最终裁决者；审核通过后进入过渡期，**不直接切换**。

### 3.4 过渡期（≥1 个项目，双轨运行）

1. 新旧流程并行运行于 ≥1 个真实项目：新流程作为主执行，旧流程作为对照回放；
2. 对比判据：六维回归打分新流程不劣于旧流程（"不降回归"在单项目上的落地版）；
3. 过渡期内旧 tag 与新 tag 并存，任何时刻可回退；
4. 过渡期结束评估：不劣 → 正式切换（更新 VERSION + CHANGELOG + 打 tag）；劣 → 回滚旧版 + 提案归档 ARCHIVE/ + pattern 保留。

### 3.5 状态机

```
触发(不适配判定) → proposed → 双倍验证 → transition(双轨≥1项目)
                                  ↓ 不劣          ↓ 劣化
                              accepted          rejected(ARCHIVE, pattern 保留)
                                   ↑
         conditional-accept(冷启动豁免+回补期限) → 逾期 → suspended
```

## 四、与 GATE.md 分级条款的映射

| GATE 级 C 条款 | 本流程落点 |
|---|---|
| 满足通用门槛全部 | 3.3 独立门控逐条核验 |
| 双倍验证（交叉验证 + 人工复审） | 3.3 第 2 步 |
| 保留旧版本 tag，更新 CHANGELOG | 3.2 + 3.4 第 4 步 |
| 过渡期 ≥1 项目双轨运行 | 3.4 全节 |

## 五、反工程师人格污染声明

本机制以"探针、回滚、tag、状态机"等词描述——这些是底座自身机制的原生概念（来自 wikiskill/演化循环语境），不是强加给任务的软件术语。对**任务**语言的要求由 route-intake 第 3 步"领域抽象映射"保证；对**机制**语言的要求是：任何新增机制概念必须能被非软件执行者理解（宪法第 5 条）。

## 六、冷启动声明

本节全部阈值（N=5 校准样本、≥2 轮失分、过渡期 ≥1 项目等）为 v0.1 假设值，未经真实数据校准；不宣称"已通用"。
