# SKILL — downstream-verify（下游验证）

## 定位
对任何存在"对外可见面"的变更，以消费者/下游身份做端到端验收；把"生产者完成"
与"下游生效"区分开。诞生依据：pattern `downstream-view-gap`（2026-09-13 蒸馏，
四条真实轨迹：6f 顺序 bug、版本元数据漂移、feedback 半落地、快照滞后误读）。

## whenToUse（何时加载）
- 任何对外变更之后：站点发布/重发布、README/USAGE/文档宣称更新、Release、
  API/命令行入口变更、凡"别人会看见或用到"的东西；
- 收到下游疑问（"怎么没更新"）时优先排查本技能清单；
- 纯内部变更无需加载，但提案须声明"无下游可见面"。

## 步骤（四步，缺一不可）
1. **枚举下游可见面**：列出本次变更的所有消费者触点（页面 URL、仓库首页、
   文档链接、Issues、下载物），每个触点一个验收项；
2. **以消费者身份实测**：实际打开/克隆/点击，不以内部日志、rc、快照对比为验收
   证据——线上 HTTP 200 + 内容实际出现才算；
3. **核对回执通道**：每个可见面是否附带"反馈被看见"的通道（Issue/评论/链接）；
   没有回执通道的可见面记为缺陷；
4. **证据写入可见通道**：验收结果（含失败与修复）落到 Issue/governance/站点，
   不留在内部记忆。

## 硬性判据
- 发布类变更的关闭证据必须是"下游侧实测通过"，"待首次差异触发"、"rc=0"等
  生产者侧证据一律视为未验证；
- 主动制造可控差异触发最后一环，不等自然差异。

## 回滚说明
- 本技能本身无副作用（只读验收 + 写可见记录）；
- 若验收发现缺陷，回滚被验收变更（git revert / 恢复快照），修复后重跑四步。
