# PATTERN — 下游视角缺口（downstream-view-gap）

## 类型
evolution-pattern（机制级缺陷模式）

## 现象（可观察的表现）
- 链路内部一切绿灯（rc=0、gate=accept、回归 10/10），但下游用户/读者看到的仍是旧状态或坏状态；
- "发布/展示/可见性"这最后一环的缺陷，内部自检系统性看不见——直到外部观察者指出；
- 内部验证证据与下游实际效果脱节（如"dispatch rc=0"被当作发布闭环的证据）。

## 触发条件（何时会出现）
- 变更存在"对外可见面"（发布、站点、API、文档宣称、可被他人消费的产物）；
- 验证只从"生产者视角"做（看自己的日志、自己的 rc、自己的快照）；
- 最后一环的验证证据是弱证据（"待首次差异触发"、"rc=0"），而非端到端实测。

## 根因
- 生产者的验证自然收敛于自己可见的中间态，下游视角需要"换一双眼睛"；
- "内部完成"与"下游生效"之间隔着发布/刷新/可见通道，这截链路没人以验收者身份走一遍；
- 反馈回执缺少可见通道时，下游连"问题被看见了"都无从确认，缺陷只能靠偶然的外部观察暴露。

## 应对措施（可复用的步骤/规则）
1. **凡对外变更，必须从下游视角端到端验证**：不是看 rc，而是以消费者身份实际取用（打开页面、
   读 README、跑克隆、点链接）；
2. **验证证据必须是下游侧证据**（线上 HTTP 200 + 内容出现、可见通道存在回执），内部日志不算数；
3. **反馈回执必须写入可见通道**（Issue/governance/站点），不得只存内部记忆；
4. 主动制造可控差异触发最后一环（不等自然差异），把"自动动作被验证"作为关闭条件。

## 适用条件与例外
- 纯内部变更（无对外可见面）不强制下游验证，但需在提案中声明"无下游可见面"；
- 下游验证由人工（用户）执行时，以人工确认为准。
