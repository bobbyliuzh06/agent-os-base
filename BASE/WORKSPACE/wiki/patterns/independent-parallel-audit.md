# PATTERN — 并行独立审计（independent-parallel-audit）

## 类型
evolution-pattern（机制级增强模式）

## 现象（可观察的表现）
- 单一主体长期运行后，其系统性盲区沉淀为"看不见的常态"（如调度顺序漂移 15 轮无人发现）；
- 换角色 prompt 的"独立复核"仍共享同一视角惯性，发现不了新类别的问题；
- 两个真正独立的审计主体并行覆盖不同域时，盲区互补，且误报可被 orchestrator 交叉验证剔除。

## 触发条件（何时会出现）
- 任务满足 route-intake 多 agent 触发条件：并行度高 + 可独立验收 + 错误代价低；
- 存在"单 agent 基线未测"的保守默认在永久化（第六轮反馈指认）；
- 需要覆盖多个互相独立的审计域。

## 根因
- 单主体视角有固定盲区（与 downstream-view-gap 同源：生产者视角看不见自己）；
- 换 prompt 不是换视角——同一实例的记忆、惯性、已知结论会延续；
- 并行独立主体之间互不知情，覆盖互补；交叉验证步骤负责剔除误报，成本可接受。

## 应对措施（可复用的步骤/规则）
1. 满足触发条件时按 route-intake 裁决真实拆解（orchestrator + N experts），不做"改个 prompt 的假编排"；
2. 专家报告强制结构化（verdict + findings + 文件:行证据 + unverified 清单），可独立验收；
3. orchestrator 逐条交叉验证（本模式第一条实践：8 条 findings 中 5 属实、1 误报被剔除）；
4. 结果无论胜负都记录基线对比——"测过了"优于"永远没测"。

## 适用条件与例外
- 串行依赖高/错误代价高的任务仍走单 agent（route-intake 保守默认依然正确）；
- 多 agent 需要宿主能力（subagent/进程编排）；无宿主能力时如实标注不可用。

## 证据轨迹
> 真实轨迹（2026-09-13，多 agent 编排最小实验 ma-20260913）：
> route-intake 裁决拆 orchestrator+2 experts 并行审计；专家 A 抓出 dashboard/7a
> 顺序漂移等 5 条；专家 B 抓出 rollup 落后等 3 条（其中 1 条悬空对象为误报，
> 被 orchestrator 以 git 历史验证剔除）；结论：并行独立审计显著优于单 agent 基线。

## 跨领域适用性评估
- 原领域：软件工程（代码审计/并行 code review）
- 可迁移至：合规审查（多审计员并行覆盖）、学术同行评审、运营巡检——一切
  "多域覆盖 + 可独立验收"的审计场景
- 抽象层级：高（独立视角互补与交叉验证的原则）
