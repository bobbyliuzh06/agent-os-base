# route-intake — 任务路由与底座适配判断

## 目的
把任意领域的新需求映射到"可执行方案 + 技能集"，并产出**是否需提底座修改**的信号。

## 步骤

### 1. 澄清（借鉴 grill，先质询再动手）
向用户确认（如未明确）：目标、边界、输入/输出、成功判据、容错要求、是否需人机协同。

### 2. 填写任务属性表（参考 SEED/scaling.summary.md，此为可校准假设）

| 属性 | 取值 | 倾向 |
|---|---|---|
| 并行度 | 高/低 | 高 → 可考虑集中编排 |
| 串行依赖 | 高/低 | 高 → 优先单 agent |
| 工具密度 | 高/低 | 高 → 控制 agent 数 |
| 错误代价 | 高/低 | 高 → 必须集中校验 + 回放 |
| 可独立验证 | 是/否 | 是 → 可派发专家 |
| 是否软件工程 | 是/否 | 否 → 映射为"通用思维流"，不套 TDD/ADR 字面 |

### 3. 拓扑建议（保守默认：单 agent）
- 串行 + 低并行 + 少工具 → **单 agent**
- 可并行 + 多角色 + 需汇总 → **集中编排**（1 orchestrator + N 专家）
- 工具极重 / 预算紧 → 单 agent + 工具，不盲目加人
- 高错误代价 → 任何多 agent 必设集中校验

### 4. 技能集映射
- 从 `skills/` 选出适用技能（基于角色/领域，非软件任务做等价抽象）
- 若找不到匹配技能 → 标记为"待创建"，纳入任务结束时的 PROPOSAL

### 5. 底座适配判断（关键）
回答：**当前 BASE 是否适配此任务？**
触发"不适配"的条件（写入 CONTEXT.md 的"触发条件"）：
- 领域完全不在种子覆盖范围内且无等价抽象
- 任务属性表中有 ≥2 项无法用现有维度表达
- 执行中反复绕过铁律才能推进

若不适配 → 任务结束时**必须**发起对 BASE 的修改提案（架构或宪法层面）。

## 输出
一份路由记录，包含：任务属性表 + 拓扑建议 + 技能集 + 是否适配（是/否 + 理由）。

## 验证判据
- 每个新任务都先走本技能再执行
- 输出可被写入 `WORKSPACE/raw/route-<task>.md` 留痕

## 回滚
拓扑/技能集建议仅为待验证假设，由任务轨迹反馈修正。
